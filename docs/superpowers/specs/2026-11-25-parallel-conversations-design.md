# 从一条提示词发起并行会话

用户在项目看板发出一条请求。明确要求多会话时，CLI 拆出各个任务，工作台创建独立对话并提交到现有运行队列。界面以 GitHub 的 `v1.4.0` 为基线，参考图用于侧栏新增的并行会话组与进度。

## 发送规则

| 用户输入 | 发送结果 |
| --- | --- |
| 「修复登录，再补回归测试」 | 一个会话，原提示词直接执行 |
| 「下面三项各开一个会话并行做。多人聊天、文件传输、视频会议」 | 一个组，三个独立会话，自动开始 |
| 「前端和后端分别开会话处理」 | 一个组，两个独立会话，可执行的会话同时开始 |
| 「在一个会话里实现并行上传功能」 | 一个会话，原提示词直接执行 |

**已确认的默认行为**是仅在提示词明确要求分开执行或并行派发时拆分。识别针对工作分派的意图。「并行上传」「设计多会话功能」等任务内容本身照常进入单会话。明确指定一个会话时优先尊重这一要求。

本期从项目看板的「发送」进入。已有会话的回复在原会话续接。「存为待办」保存原始提示词并沿用现有待办流程。

## 拆分与执行

考虑过让主会话在工作中派发子会话。那种做法支持动态补派，前提是 Claude 和 Codex 都有工作台可跟踪的派发、取消和恢复机制。本期采用先拆分、再调度的方式。CLI 决定任务边界并撰写子提示词，工作台在所选源目录创建和调度独立会话，每个子会话自行决定实现步骤。

1. 后端对新发送请求做本地意图判断，普通任务快速进入现有创建流程。明确要求拆分时，侧栏立即显示「正在拆分任务」。所选 CLI 在独立的拆分名额内以低思考等级生成计划，按引擎支持禁用执行工具。计划完成即刷新卡片，子会话按输入框的思考等级执行。
2. CLI 为明确列出的顶层任务分别创建会话，未列项时按实际工作拆分。标题中的数量仅供参考。CLI 返回组名、会话提示词和前置任务编号，工作台检查执行内容、依赖引用和循环依赖。
3. 工作台在一个数据库事务中写入组与全量子任务，保留各项顺序，之后交由现有运行器调度。并发上限沿用 `WB_MAX_CONCURRENT`，默认同时执行 4 个。超过可用名额的会话显示「排队中」。每张卡片具有独立任务 ID、CLI 会话 ID、运行日志和审批，沿用单任务的继续、停止、重试和验收能力。
4. 子会话默认继承来源项目、执行位置、引擎、模型、思考等级和权限。用户显式指定某项使用另一引擎时，后端校验该引擎在所选位置可用并使用它的默认模型和思考等级。原始附件可供各子会话使用，删除单个子会话时保留其他会话仍引用的附件。

## 工作区和恢复

- 新组的所有子会话共享发送时选定的源目录，本机与 SSH 位置均按输入框所选权限执行。每项改动随写入出现在源目录，用户可以直接运行或自行提交。
- 每张子卡片可以在原 CLI 会话内多次续接。旧会话已绑定的 worktree 供续接及查找原改动，尚未建立工作区的旧任务使用源目录。
- 等待前置任务的会话留在待办。前置会话最近一轮成功且结果已就绪时，工作台自动启动满足条件的任务。前置任务再次执行会让下游结果待复查。已启动的下游轮次先收尾，再执行前置的新一轮，避免同时修改共享产物。前置成功后，在旧会话发送一条复查消息，仅修正或补做受影响的部分。前置失败或取消时，待办显示需要重试的任务。重启后自动调度已具备条件的待办。
- 拆分超时或返回无法执行的结果时，侧栏显示失败原因，允许从原提示词重试拆分或主动改用单会话。重复提交使用同一发送标识，同一个标识最多创建一组子会话。创建成功后，个别会话启动失败只影响自身。
- 刷新页面后按同一组 ID 恢复分组、卡片顺序和进度。应用重启后，沿用现有运行中断语义，在运行队列中未完成的任务可独立重试。拆分中断时保留可重试的记录，已生成的会话沿用原 ID。

## 侧栏与看板

侧栏沿用 `v1.4.0` 的宽度、字号、主题、状态分组顺序和普通任务样式，并在分组内增加紧凑的并行会话组。

- **组头**位于侧栏「进行中」下，沿用原主题的蓝色，显示图标、组名、折叠箭头、完成数、百分比和进度条。新组默认展开，折叠状态按组保存。展开时以细线连接缩进的子卡片。
- **子卡片**按 CLI 给出的顺序排列，沿用普通任务项的两行样式，显示会话标题、引擎、编号和进度，点击可进入真实会话。失败、取消和排队时显示对应状态。组内还有排队或执行中的会话时，整组留在「进行中」。全部结束后，有待验收会话的组进入「待验收」，其余进入「最近」。每组始终只有一个侧栏入口。
- **整组进度**按当前状态为「待验收」或「已完成」的会话数除以组内会话总数计算。三项都在跑时显示 `0/3 · 0%`，一项进入「待验收」后显示 `1/3 · 33%`。失败和取消提供独立的状态标记。重试和续接沿用原卡片和原分母，并按当前状态更新进度。删除已结束的会话会重算组内总数，删除最后一项后移除组。
- **单会话进度**由引擎归一化的当前轮计划事件提供，按已完成计划步骤数计算。尚未收到可计算的进度时显示「执行中」。会话成功执行后显示 100%，新一轮开始时清除旧进度。
- **主区域**使用 `v1.4.0` 的看板、列表、对话、工具栏和输入框。各子会话走原有任务卡片及状态列。发送并行请求后保留当前视图，展开侧栏的任务组。
- **交互**复用当前项目切换、搜索、额度栏和键盘导航。搜索匹配组名时展示组内会话，匹配单个会话时保留它的组头。组进度始终按全组计算。系统深色模式使用项目现有色板提供同样的层级。

## 实现边界

现有任务仍以 `tasks` 和 `runs` 保存。增加任务组及可空的成员关系，普通任务在增量迁移后沿用原数据。API 继续支持现有任务创建与执行，工作台的新发送入口返回单个任务或组的标识，避免改变现有调用方的响应形状。数据库写入留在 `db`，编排留在 `services`，CLI 计划解析留在 `engines`，调度和进度事件进入现有运行链路，Vue 负责展示。

## 验收

1. 发送示例提示词后正好出现三张会话卡片。每张卡片的会话标识和日志独立，在并发名额足够时有重叠的运行时间。单会话请求、内容中的「并行」和会话内回复继续走原路径。
2. 用可重复的 CLI 测试数据覆盖拆分失败、数量校验、无法独立执行的任务、重复提交、排队、个别失败、重试、删卡后进度、共享附件删除和数据库迁移。子任务失败时其余任务继续运行。
3. 运行 `.venv/bin/python -m pytest -q`。再用 `WB_KEYCHAIN_SERVICE=workbench-ssh-dev .venv/bin/python -m workbench --debug --data-dir .devdata/desktop` 从源码启动原生窗口。验证三会话派发、进度更新、打开子卡片、折叠和重启后分组恢复。
4. 比对 GitHub 的 `v1.4.0` 标签，核对侧栏任务列表之外的页面模板和样式，以及原状态分组与看板逻辑。原生窗口中检查侧栏组头、进度条、三张缩进卡片及原版看板和输入框。
5. 验证三个会话并行写入所选的同一个源目录。打开一张子卡片并连续发送两条调整，核对它们与首次执行使用同一个 CLI 会话且直接更新该目录。
